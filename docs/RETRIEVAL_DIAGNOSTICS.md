# 检索诊断工作台

v0.7 在现有检索评测上增加逐题诊断：同一个开发问题，在 BM25、Dense、Hybrid 中分别找到了哪段原文，证据在什么阶段缺失，以及补充相邻分块后是否完整进入上下文。报告由代码生成，保存 JSON 与可直接打开的独立 HTML；页面只读，不修改问题或人工审核状态。

v0.8 支持 `--context-policy merged_neighbors`，生成合并证据的准确范围和组成块编号。默认仍为 `neighbors`；规则、预算配对实验和边界见 [上下文合并说明](CONTEXT_PACKING.md)。本页原有命令及 v0.7 历史报告继续使用默认策略。

## 运行

当前无需密钥。即使 `.env` 已配置远程模型，本命令默认也强制 Hashing Embedding，不调用生成模型。

```powershell
.\.venv\Scripts\python.exe -m scripts.diagnose_retrieval `
  --output work/diagnostics/development.json
```

打开 `work/diagnostics/development.html`。无需后端服务、CDN 或联网。再次运行请使用新的输出名，已有 JSON 或 HTML 均不会覆盖。原始 JSON 是数据记录，HTML 内嵌同一份数据；可迁移到其他机器查看。

本轮保存的开发记录为 `evaluation/reports/retrieval-diagnostics-v07.json` 和同名 HTML。默认使用固定官方语料、47 道开发候选题、章节分块 500 字符/重叠 80、Top-K=5、上下文预算 16000 字符。41 道有证据的可回答题参与诊断；6 道拒答或澄清题跳过，没有运行 8 道保留测试题。

可调整实际检索和预算参数后另存报告，例如：

```powershell
.\.venv\Scripts\python.exe -m scripts.diagnose_retrieval `
  --top-k 3 --chunk-size 500 --chunk-overlap 80 `
  --context-char-budget 1200 --strategies bm25 `
  --output work/diagnostics/bm25-k3-budget1200.json
```

预算表示进入上下文的分块正文字符总和；重叠内容重复占用预算，整块超过剩余预算便跳过，后面的短块仍可能被纳入。这与服务当前策略一致，不是 token 上限。预算变化实验只能用来分析取舍，不能把不同预算的覆盖率直接描述为公平提升。

用户后续配置模型后，可显式加 `--configured-embeddings` 使用现有 Embedding 适配器；这时可能产生真实接口请求。该模式仍不调用生成模型。`--questions` 可指定另存的开发审核文件，配合 `--require-reviewed` 拒绝未审核问题。工具仅接受 `--split development`，不提供测试集调试入口。

## 诊断规则

每条证据是规范化原文中的左闭右开字符区间。统计的是同来源分块区间的并集；重复与重叠不会抬高覆盖率，多块拼接可以构成完整覆盖。页面用 Python Unicode 字符数对齐，包括中文和 emoji。

| 阶段 | 实际计算 |
|---|---|
| 全部索引 | 所有已生成分块是否保留标注区间 |
| 版本过滤后 | 满足该题 product/version 的分块覆盖范围 |
| 诊断候选池 | 当前策略最终返回的前 50 个分块 |
| Top-K | 诊断池前 K 个分块，K 范围为 1–50 |
| 无预算扩展 | 按服务规则添加同文档同章节相邻块，临时放宽预算，仅做诊断 |
| 实际上下文 | 应用实际字符预算后的分块 |

Hybrid 仍先从 Dense、BM25 各取 50 个，再以现有 RRF 融合。诊断池是融合后的前 50，可能小于两路候选并集；“池外”不证明两路原始召回都没有该片段。限制 K≤50 是为了让诊断池前缀与服务直接查询 K 时的 RRF 输入池一致，已有回归测试验证。

每条证据按以下顺序得到一个主要状态，同时保留所有阶段覆盖值：

| 状态 | 可核对的条件 |
|---|---|
| 上下文完整覆盖 | 实际上下文覆盖全部标注字符 |
| 索引未完整保留标注范围 | 所有分块的并集也不能完整覆盖；可检查边界丢失的换行等字符 |
| 过滤后证据不完整 | 全索引覆盖完整，版本过滤后的覆盖不完整 |
| 预算截断证据 | 无预算扩展完整覆盖，实际预算下不完整 |
| 证据在候选池内、Top-K 外 | 池内可以完整覆盖，但 Top-K 及相邻扩展仍不足 |
| 候选池未完整覆盖证据 | 前面的情况均不满足，诊断池仍无法完整覆盖 |

如果多个因素共同发生，主要状态不代表唯一原因。例如索引缺失且预算也损失部分覆盖时，主要状态是索引缺失，同时 `coverage_lost_to_budget` 仍为 true。另记录相交分块、首次相交排名、按排名累计完整覆盖的位置、是否需要多个分块、相邻块是否补回证据、预算未纳入的分块。

“文档命中但证据不完整”筛选要求 Top-K 命中至少一份相关来源，同时没有完整覆盖该题所有标注范围。上下文之后可能将证据补回，因此筛选结果中可以出现“上下文完整覆盖”。

策略总览使用全部可诊断开发题为固定分母；不随页面搜索或版本筛选改变，并在标题标明。完整覆盖题数要求该题所有证据都完整，而逐题证据召回为完整覆盖的证据条数 / 证据条数。缺少证据、拒答和澄清题单独计数，不记成召回成功或失败。

## 三分钟演示

1. 先说明当前是离线开发工具、候选题未经过人工审核，Dense 是 Hashing 演示向量。
2. 选 BM25，再筛选“文档命中但证据不完整”，解释为什么文档级命中会掩盖段落定位问题。
3. 清除现象筛选，搜索 `support-007`，切换 BM25 和 Dense 查看同一道后台任务问题。当前保存的 Hashing 记录中，Dense 的完整证据在第 31 位，而 Top-5 命中的同文件段落没有覆盖答案范围。展开相交分块，核对原文及位置。
4. 清除搜索，筛选“相邻分块补回证据”，查看 Top-K 与上下文覆盖的变化，同时指出字符消耗变化，避免直接宣称算法增益。
5. 展开复现信息，说明报告保存了配置、问题/语料/分块/代码/HTML 模板指纹，原始标注和测试集保持独立。

可用于简历的能力表述：实现开发集逐题检索诊断工具，对比 BM25、Dense 与 RRF，基于字符范围并集定位候选排序、版本过滤与上下文预算问题，并生成带数据和代码指纹的离线交互报告。

不能据当前结果写“提高了检索准确率”“支持生产规模”或“真实模型验证有效”。本轮没有改变检索算法，也没有新增、人工审核或扩充问题；工具解释的是当前候选锚点的覆盖现象，不能独立证明语义根因或答案正确性。

## 验证与文件

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check app scripts tests
.\.venv\Scripts\python.exe -m scripts.evaluate --demo --report-name latest
```

核心实现为 `app/diagnostics.py`；生成器为 `scripts/diagnose_retrieval.py`；独立页面模板为 `app/static/diagnostics.html`；回归测试为 `tests/test_diagnostics.py`。GitHub Actions 已增加离线报告生成及产物保存步骤，远端尚未触发。无需新增依赖。

HTML 内嵌原文和问题，分享报告意味着分享这些内容；页面使用文本节点渲染外部内容、转义内嵌 JSON 的 `<`，并通过 CSP 禁止远程资源和网络请求。当前提交范围使用公开的官方语料；若换成自己的文档，应自行选择报告分享范围。
